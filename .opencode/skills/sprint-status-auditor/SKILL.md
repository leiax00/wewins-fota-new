# Sprint Status Auditor

用于“核对某个 Sprint/迭代是否完成”并“把文档任务状态更新到与代码一致”的标准技能。

## 适用场景

- 用户要求评估某个 Sprint 的完成度
- 用户要求核对计划文档与实际实现是否一致
- 用户要求将“已实现但未勾选”的任务更新为完成
- 需要输出“剩余工作清单”

## 核心原则

1. 只基于证据判定，不凭主观推测
2. 代码实现优先于历史文字描述
3. 仅更新“已实现但未标记”项，不虚标完成
4. 明确区分“已实现”“部分实现”“未实现”
5. 更新后必须进行文本与差异复核

## 执行流程

### Step 1: 定位迭代文档与目标范围

必做：
- 定位 Sprint 计划文档（通常在 `docs/05-plans/`）
- 提取文档中的：
  - 验收标准清单
  - 任务清单（表格状态列）
  - 进度百分比/阶段状态
  - 变更日志

建议工具：
- `glob`: 查找 `*sprint*.md`
- `grep`: 搜索 `Sprint`、`验收标准`、`任务清单`、`状态`
- `read`: 阅读目标文档关键片段

### Step 2: 并行收集实现证据（必须并行）

必做：
- 启动 1-2 个 `explore` 任务，分别聚焦：
  - 文档条目到代码实现映射
  - 核心功能与测试覆盖现状
- 同时使用直接工具做精准检索：
  - `grep`/`ast-grep`：定位关键类、方法、配置、测试
  - `read`：核验关键实现细节

判定口径：
- **已实现**：存在可运行实现入口，且逻辑完整
- **部分实现**：存在骨架/部分逻辑，但关键路径未闭环
- **未实现**：仅文档描述，无对应实现证据

### Step 3: 建立“文档项 -> 代码证据”映射

为每个文档任务条目记录：
- 文档条目名称
- 当前文档状态（✅/⏸️/[ ]）
- 实际实现状态（已实现/部分实现/未实现）
- 证据文件路径（可附行号）
- 是否需要更新文档（是/否）

### Step 4: 更新文档状态（仅改需要改的项）

允许更新内容：
- 任务表状态（如 `⏸️ -> ✅`）
- 验收标准勾选（如 `[ ] -> [x]`）
- 进度追踪文字（百分比、阶段描述）
- 变更日志新增“本次核对与校准”条目
- 文档版本号与最后更新时间

禁止行为：
- 没有证据时标记完成
- 删除未完成项
- 修改与本次 Sprint 无关章节

### Step 5: 复核与输出

必做复核：
- `git diff` 仅包含预期文档修改
- 文档中“前后状态”一致（任务表、验收项、进度、变更日志不冲突）
- 保留明确剩余项

输出内容应包含：
- Sprint 是否完成的结论
- 已自动更新的文档项
- 仍待完成项（按优先级）
- 每项结论对应的证据路径

## 推荐工作模板

### A. 分析结论模板

```text
结论：Sprint X 为“已完成/部分完成”。

已完成但文档未标记（已同步更新）：
1) <条目A> -> 证据: <path:line>
2) <条目B> -> 证据: <path:line>

仍需完成：
1) <条目C>（原因）
2) <条目D>（原因）
```

### B. 文档更新模板（变更日志）

```text
### YYYY-MM-DD (进度核对与文档校准 - vX.Y)
- ✅ 状态修正: <条目1>
- ✅ 状态修正: <条目2>
- 📊 进度修正: <old>% -> <new>%
- ⏸️ 当前剩余: <未完成项列表>
```

## 质量门禁清单

- [ ] 已并行完成上下文收集（explore + 直接工具）
- [ ] 每个“标记完成”的条目都有代码证据
- [ ] 文档内状态一致（任务表/验收标准/进度/变更日志）
- [ ] 输出包含剩余工作清单
- [ ] 未越界修改其他 Sprint 文档

## 注意事项

- 如果存在“实现与文档描述冲突”，以代码真实行为为准，并在变更日志中注明“状态校准”。
- 如果性能/覆盖率类指标无可验证报告，不应标记完成。
- 该技能默认只做“状态核对 + 文档更新”，不主动扩展实现新功能。

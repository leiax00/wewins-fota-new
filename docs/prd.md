# 千万级设备 FOTA 管理平台产品需求说明书 (PRD)

## 1. 文档概述

### 1.1 项目背景

本系统旨在为千万级 IoT 设备提供安全、稳定、可控的固件远程升级（Field Over-the-Air）服务。通过高性能的架构设计，解决高并发下的请求响应、大数据量的实时统计以及复杂的灰度发布需求。

### 1.2 核心价值

* **高可用性**：支撑千万级设备并发检查更新，不压垮后端数据库。
* **精细化运营**：支持基于标签和 Hash 的灰度发布，实时监控升级进度。
* **低成本统计**：利用 Redis Bitmap 实现亿级数据的实时在线与沉默统计。

---

## 2. 业务架构与流程

### 2.1 系统架构图

系统采用 **Java + Redis + PostgreSQL + ClickHouse + RabbitMQ + RustFS** 的黄金组合。

### 2.2 核心升级流程

1. **设备请求**：设备携带 `imei`, `product_id`, `version` 访问 API。
2. **身份与限流**：API 通过 Redis 校验设备身份并执行请求限流。
3. **策略匹配**：
* 匹配产品与版本号。
* 通过 `Hash(imei) % 100` 判断是否命中灰度。
* 校验时间窗口与任务配额（Redis 计数器）。


4. **下发响应**：返回 RustFS 生成的带签名下载 URL（内嵌 `policy_id`）及下一次检查间隔 `next_check_interval`。
5. **异步审计**：日志通过 RabbitMQ 写入 ClickHouse，设备活跃状态更新至 Redis Bitmap 和 PostgreSQL。

---

## 3. 功能需求

### 3.1 产品与版本管理

* **产品建模**：支持多产品管理，每个产品拥有独立的密钥。
* **版本控制**：
* 上传固件包至 RustFS。
* 自动计算 MD5/SHA256 校验码。
* 支持全量包与差分包标记。



### 3.2 策略即任务管理 (Unified Strategy)

系统将升级规则与执行过程合二为一。

* **范围控制**：支持按版本号数组、特定设备标签（JSONB）筛选。
* **灰度发布**：支持 0-100% 的步进控制。
* **执行控制**：
* **时间窗**：设定任务的开始与结束时间。
* **总量限额**：设定本次策略最大允许升级的设备总数。
* **熔断开关**：一键停止策略下发。



### 3.3 设备中心

* **设备画像**：记录 IMEI、自增 ID（Bitmap Offset）、当前版本、硬件标签。
* **状态追踪**：异步记录 `last_seen` 时间，记录设备所有的升级历史轨迹。

---

## 4. 统计与监控需求 (核心重点)

### 4.1 实时在线统计 (Redis Bitmap)

* **功能**：实时显示今日活跃设备数（DAU）。
* **实现**：利用设备自增主键作为 Offset，在 Redis 中按天存储位图。
* **优势**：1 亿数据仅占 12MB，`BITCOUNT` 耗时 < 3ms。

### 4.2 离线/沉默统计

* **离线 3/7/30 天**：通过 Redis `BITOP`（位运算）计算多个日期位图的并集与差集。
* **流失分析**：在 Redis + Prometheus + Grafana 中直观展示沉默设备趋势。

### 4.3 升级质量审计 (ClickHouse)

* **进度监控**：各版本的升级成功率、下载失败原因分布。
* **日志溯源**：通过下载 URL 中携带的 `policy_id`，实现日志与策略的精准对齐。

---

## 5. 非功能性需求

### 5.1 性能指标

* **API 响应**：99% 的检查更新请求在 50ms 内完成。
* **并发能力**：通过横向扩展 Java 节点，支撑 10,000+ QPS。
* **带宽控制**：通过 CDN 分发流量，利用控制字段随机化设备下载时间（Jitter），防止带宽瞬间过载。

### 5.2 安全性

* **防篡改**：固件包必须强制进行哈希校验。
* **防刷单**：下载链接必须有时效性（S3 Pre-signed URL）。
* **频率限制**：Redis 限制单个设备在 1 小时内只能执行一次有效的 `last_seen` 写入。

## 6. 数据字典 (核心表结构)

### 6.1 设备表 (PostgreSQL)

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | SERIAL | 主键，Redis Bitmap 的 Offset |
| `imei` | BIGINT | 业务唯一 ID，建唯一索引 |
| `tags` | JSONB | 设备属性（地区、批次等），建 GIN 索引 |
| `last_seen` | TIMESTAMP | 异步更新，最后心跳时间 |

### 6.2 策略表 (PostgreSQL)

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | SERIAL | 策略/任务 ID |
| `gray_rate` | INT | 灰度比例 (0-100) |
| `max_limit` | INT | 最大升级名额 |
| `next_interval` | INT | 下发给设备的轮询周期 |

## 7. 后续规划

1. **分片策略**：当 ID 超过 1 亿时，启动 Redis Bitmap 分片存储。
2. **CDN 预热**：策略开启前，自动触发 CDN 预热，降低 RustFS 回源压力。
3. **长连接增强**：引入 MQTT，实现关键安全补丁的“强制推送（Push）”。

## 8. 设备与服务端交互流程规范

### 8.1 交互时序图

该时序图展示了从设备发起检查到完成升级的完整闭环，重点在于**异步日志上报**与**业务主流程**的分离。

---

### 8.2 核心交互阶段详解

#### **阶段一：检查更新 (Check Update)**

这是压力最大的接口，必须保持高度轻量。

* **设备请求 (GET /v1/upgrade/check)**

|名称|位置|类型| 必选 |说明|
|---|---|---|----|---|
|product|query|string| 是  |产品名称|
|imei|query|string| 是  |imei|
|version|query|string| 是  |设备当前版本|
|auto|query|string| 否  |0: 手动; 1: 自动|
|lang|query|string| 否  |语言|
|tag|query|string| 否  |设备当前tag|
|dev|query|string| 否  |当前是否是开发环境, 1表示是, 不填或0表示否|

* **设备请求 (POST /v1/upgrade/check)**
```json
{
    "product": 861234567890123,
    "imei": 861234567890123,
    "version": "v1.0.2",
    "auto": 0,
    "lang": "en",
    "tag": "build01",
    "dev": 1,
    "extTags": { "region": "CN", "model": "T1" }
}

```


* **服务端逻辑**：
1. **身份校验**：从 Redis 缓存获取产品配置。
2. **状态标记**：执行 `SETBIT` 更新当日活跃位图。
3. **策略匹配**：判定 IMEI 是否在灰度桶内。
4. **生成 URL**：调用 RustFS SDK 生成带过期时间的签名链接。


* **服务端响应**：
```json
{
   "release_start_date": "2026-02-03T10:28:56",
   "release_note": "xxxxxxx",
   "new_firmware": "v2.0.0",
   "download_url": "https://cdn.xxx.com/pkg.bin?p_id=101&sig=...",
   "file_size": 20000000,
   "file_size_text": "19MB",
   "control": {
      "checkInterval": 86400,
      "downloadDelay": 300
   }
}

```



#### **阶段二：固件下载 (Download)**

* **行为**：设备根据响应中的 `downloadDelay` 随机休眠后，发起 HTTP GET 请求。
* **鉴权**：CDN 边缘节点或 RustFS 自动校验 URL 中的签名参数。
* **解耦**：此过程不占用 Java 服务端资源，流量完全走 CDN。

#### **阶段三：进度与结果上报 (Event Report)**

为了保证系统实时监控升级进度，设备需在关键节点异步上报状态。

* **上报请求 (POST /v1/upgrade/report)**
```json
{
   "imei": 861234567890123,
   "url": "http://foid-dl.xxx.com/xxx.bin?xxxxxx",
   "event": "", // 状态枚举： DL_START, DL_OK, DL_FAIL, UP_OK
   "details": {}
}

```


* **服务端处理**：
1. API 接收请求后，直接丢入 **RabbitMQ**。
2. **立即返回 200 OK**（不等待数据库写入）。
3. **Consumer 消费**：批量将日志写入 **ClickHouse**；如果是 `UP_SUCCESS`，则异步更新 **PostgreSQL** 中的设备当前版本号。



---

### 8.3 异常处理逻辑 (Retry & Backoff)

在千万级设备环境下，错误的重试策略会导致“重试风暴”，压垮服务器。

1. **退避算法 (Exponential Backoff)**：
   如果设备请求 API 失败（如 503 繁忙），下次重试时间应遵循  增长，并叠加随机抖动（Jitter）。
2. **静默期控制**：
   如果 API 返回 `checkInterval` 为 0 或特定错误码，设备应进入“静默模式”，在接下来的 24 小时内禁止再次请求。
3. **断点续传**：
   固件下载必须支持 HTTP Range 请求。设备下载中断后，应从上次偏移量继续，减少 CDN 带宽浪费。 (目前我们的设备不支持，不做强制要求)

## 9. 交互安全性设计
-- 暂时不实现

1. **请求签名 (API Sign)**：
   设备请求 API 时，需使用出厂预埋的 `ProductSecret` 对请求体进行 HmacSHA256 签名，防止他人恶意伪造 IMEI 请求。
2. **双重校验**：
* **下载前**：校验 URL 签名。
* **安装前**：设备端必须对下载完成的 `.bin` 文件进行完整性校验（MD5/SHA256）以及厂商私钥的签名校验。

### 总结

这套交互流程实现了**逻辑上的闭环**：

* **API 层**负责轻量级的“决策”。
* **CDN 层**负责沉重的“分发”。
* **MQ/ClickHouse** 负责详尽的“记录”。
